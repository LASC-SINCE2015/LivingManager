# 0007 「元に戻す」では更新者を自分にし、ほかの人の担当は戻さない

- 状態: 採用
- 日付: 2026-10-25

## 状況

ステータス変更と購入完了のあとに「元に戻す」を出す（仕様）。単純に「操作前の値をすべて書き戻す」と、次の問題がある。

- 操作前の更新者がほかの人だった場合、その人を更新者として書くことになる。ほかの人になりすました記録はデータの保護の仕組み上書けない。
- 「十分」に変えたときにほかの人の担当を解除していた場合、その人の担当を書き戻すことになる。担当者として書けるのは本人だけ（[0005](0005_purchase_does_not_change_updater.md) と同じく、記録の正しさを保つため）。
- 「元に戻す」を押すまでの数秒の間に、ほかの人が同じアイテムを変更しているかもしれない。

## 決定

- 「元に戻す」はトランザクションで読み直し、**自分が変えたままのときだけ** 戻す（`revertStatus` / `revertPurchase`）。ほかの人が変更していたら何も書かず、「ほかの人が変更したため戻せませんでした」と表示する。
- 戻すときの更新者は自分（元に戻した人）、`updatedAt` はサーバー時刻にする。
- 「十分」に変えたことで解除した担当は、自分の担当なら元の値（`at` も元のまま）に戻し、ほかの人の担当は解除したままにする。
- 「残りわずか」⇄「切れてる」の変更を戻すときは、今の担当をそのまま残す。
- 購入完了を戻すときは、戻せるアイテムだけを戻し、戻せなかった件数を表示する。

## 理由

- 「最後に在庫情報を変えたのは誰か」という記録として、元に戻した人を更新者にするのは事実に合っている。
- ほかの人の変更を消さないことで、元に戻す操作が新たな食い違いを生まない。
- Cloud Functions を使わずに実現できる（[0001](0001_no_cloud_functions.md)）。

## 影響

- 元に戻したあとの更新者・更新日時は、操作前とは違う（元に戻した人・時刻になる）。
- ほかの人の担当を誤って解除した場合、元に戻しても担当は戻らない。その人にもう一度「買います」を押してもらう必要がある。
- 「十分」に変えるときにほかの人の担当があれば確認ダイアログを出しているため、誤って解除する場面は少ない。
