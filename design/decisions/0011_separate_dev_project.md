# 0011 テスト環境は本番とは別の Firebase プロジェクトにする

- 状態: 採用
- 日付: 2026-11-03

## 状況

アプリを公開し、家族が本番の環境で毎日使うようになった。これからの機能追加やルールの変更を、家族のデータに影響を与えずにスマホ・PC の実機で確かめられる場所が必要になった。Spark（無料）プランの範囲で用意したい（[0001](0001_no_cloud_functions.md)）。

## 決定

- **テスト環境として、本番とは別の Firebase プロジェクトを作る。** Hosting・Firestore・Authentication・許可リストはすべて本番と分かれる。
- **設定ファイルを環境ごとに分け、`APP_ENV`（`prod` / `dev`）を持たせる。** `dev` でビルドしたアプリは、左上に「テスト」の帯を出し、タブの名前とバージョン表示にもテスト環境であることを出す。
- **デプロイは `tools/deploy.ps1` で行い、デプロイ先は設定ファイルの `FIREBASE_PROJECT_ID` から決める。** 本番へのデプロイは実行前に確認を求める。
- 流れは「機能ブランチ → develop → テスト環境で確認 → master → 本番」とする。

## 理由

- 同じプロジェクト内の Hosting のプレビューチャンネルでは、Firestore と Authentication が本番と共用になる。データ構造やルールの変更を試すと家族のデータに響くため、確認の場所としては足りない。
- エミュレーターはルールのテストには向いているが、PC の中でしか動かないため、スマホでの確認には使えない。
- 別プロジェクトにしても Spark プランのままで費用はかからず、新しく入れるツールもない。
- ビルドの設定とデプロイ先を別々に指定すると、テスト環境の設定のアプリを本番に出すといった取り違えが起こりうる。1 つの設定ファイルから両方を決めれば、その心配がない。

## 影響

- テスト環境の許可リストは本番とは別に管理する。テスト環境で使うアカウントは、テスト環境のプロジェクトに個別に登録する。
- Firestore のルール・インデックスは、テスト環境と本番の両方にデプロイする必要がある（テスト環境で確かめてから本番へ）。
- テスト環境のデータは本番から自動ではコピーされない。確認に必要なデータはテスト環境で作る。
- `APP_ENV` を書き忘れた設定ファイルでビルドすると、本番として扱う（帯が出ない）。`tools/deploy.ps1` は `APP_ENV` がない設定ファイルではデプロイしない。
